# 测试规范

## 测试基础设施

- **Swift 包测试：** Swift Testing
- **APP 模型测试：** XCTest
- **端到端 UI 测试：** XCUITest
- **项目生成：** `xcodegen generate`
- **M1A 总验证：** `bash scripts/verify-m1a.sh`
- **当前状态：** M1A 已建立包测试、APP 模型测试和 iPhone/iPad UI 测试；实际通过情况以总验证脚本的当次输出为准

## 测试组织

- Swift Package 测试放在对应包的 `Tests/<Module>Tests/`。
- APP 单元测试放在 `PokerCoachTests/`。
- UI 测试放在 `PokerCoachUITests/`。
- 共享测试夹具放在同一测试目标的 `Support/`，不得成为生产 API。
- 每个测试使用固定 UUID、日期和发牌种子，避免依赖执行顺序或全局状态。

## TDD 循环

每个实现任务按以下顺序执行：

1. 写出能表达具体行为的失败测试。
2. 运行测试并确认因缺失行为而失败。
3. 写最小实现。
4. 运行目标测试并确认通过。
5. 运行受影响模块的完整测试。
6. 提交。

## 必测规则

- 筹码守恒、底池和合法行动。
- 策略频率总和、非法行动、重复牌和内容版本。
- EV 损失、混合策略和结果独立性。
- 训练事件幂等、排序和损坏处理。
- 能力画像、信心校准和训练优先级。
- iPhone/iPad 主流程、动态布局和离线状态。
- Release 不包含开发策略 fixture。

## 通过标准

- 测试命令退出码为 0。
- 不允许用删除断言、放宽核心约束或仅验证“不崩溃”来使测试通过。
- 测试失败修复必须覆盖根因，不只改变期望值。
- Harness task 通过规格符合性和代码质量双阶段评审后才可完成。

## 确认测试真的在验证

退出码为 0 只说明没有失败，不说明有断言被执行。以下情况必须主动排除。

- 使用 `-run`、`-only-testing` 等过滤时，核对实际执行的用例数，确认没有用例被静默排除。测试名与过滤表达式不匹配是最常见的原因。
- 断言必须作用于真正承载语义的表示。篡改类断言不要改动编码后的文本，要改动解码后的字节：base64 末字符可能只含填充位，改它解码结果不变，测试会偶发通过而实际未做任何校验。
- 涉及并发、时序或随机输入的测试，用 `-count` 重复执行确认稳定；偶发通过的安全测试比没有测试更危险，因为它会让人误以为该约束受到保护。
